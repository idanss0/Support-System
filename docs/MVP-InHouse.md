# Support Control Tower: חלופה לפיתוח פנימי (בלי Spotfire)

| | |
|---|---|
| **תאריך** | 2026-10-12 |
| **בעלים** | מנהל התמיכה הטכנית |

| **מה לא משתנה** | Salesforce נשארת מערכת התמיכה (קייסים, בקשות, SLA). ה-DW נשאר מקור הנתונים |

## 0. תקציר והמלצה

**ההיקף זהה ל-MVP המקוצר:**
- שכבת נתונים מינימלית ב-DW.
- מסך חי לראשי הצוותים: P1 פתוחים, SLA בסיכון ובקשות לא משויכות.
- קישור מכל שורה ל-Salesforce.

ההבדל היחיד הוא מי מציג את המסך: במקום Spotfire, אפליקציית ווב פנימית.

| | Spotfire (MVP 2.0) | פיתוח פנימי (המסמך הזה) |
|---|---|---|
| זמן עד עלייה לאוויר | כ-4 שבועות | כ-7 שבועות |
| רענון "חי" | תלוי במה ש-Spotfire מאפשר (לאימות מול הספק) | בשליטה מלאה. יעד: עד 30 שניות, ואפשר להגיע לשניות |
| עלות ישירה | רישיונות ויועץ | זמן פיתוח, ובלי רישיונות |
| תחזוקה | הספק מתחזק את הפלטפורמה, ו-IT מתחזק את הניתוח | **הצוות הפנימי מתחזק הכול, לתמיד**: קוד, שרת, אבטחה ועדכונים |
| גלים הבאים (טרנדים, איכות לפי גרסה, בתי חולים) | קל: גרפים וסינונים מובנים | כל גרף הוא קוד שצריך לכתוב ולתחזק |
| אפליקציה לטלפון בהמשך | אפליקציה נפרדת | **אותו API משרת גם את אפליקציית הטלפון** (ראו מסמך MVP-Mobile) |
| אבטחה ו-HIPAA | הספק אחראי לפלטפורמה | הארגון אחראי לכל השכבות, כולל בדיקת חדירות |

**ההמלצה שלי:**
- **פיתוח פנימי מתאים למסך החי.** זה מסך תפעולי, ולא כלי ניתוח: שלושה מספרים ושתי רשימות שחייבים להתעדכן מהר. כאן שליטה מלאה ברענון שווה יותר מגמישות של כלי BI.
- **פיתוח פנימי לא מתאים לגלים האנליטיים.** אם בהמשך תרצו טרנדים, דירוגים וחיתוכים, לבנות כל אחד מהם בקוד יהיה יקר ואיטי בהרבה מכלי BI.
- **המסקנה:** אם בוחרים בפיתוח פנימי, כדאי להחליט כבר עכשיו מה עושים עם הגל האנליטי. האפשרויות: כלי BI אחר שכבר יש בארגון, או תקציב פיתוח מתמשך.

## 1. הבעיה והפתרון

**הבעיה:** ראשי הצוותים לא רואים במקום אחד מה דורש טיפול עכשיו: אילו קייסים קרובים להפרת SLA, אילו P1 פתוחים, ואילו בקשות אסקלציה עדיין בלי בעלים. כדי לדעת את זה היום צריך להריץ כמה דוחות ב-Salesforce.

**הפתרון:** אפליקציית ווב פנימית עם מסך אחד, שמתעדכן לבד כל 30 שניות. היא נפתחת בכל דפדפן: במחשב, על מסך הקיר ובטלפון. כל שורה במסך נפתחת כרשומה ב-Salesforce.

## 3. הפיצ'רים ההכרחיים (Core Features)

| # | פיצ'ר | מה בדיוק |
|---|---|---|
| F1 | **שכבת נתונים מינימלית ב-DW** | views על רשומות פתוחות בלבד: `Case`, `CaseMilestone`, `Request`, ושמות מ-`User`, `Group` ו-`Account`. זהה ל-MVP 2.0 |
| F2 | **מסך חי** | שלושה אריחים: P1 פתוחים, SLA בסיכון ובקשות שממתינות לשיוך. שתי רשימות: SLA בסיכון (לפי הזמן שנשאר) ובקשות בלי בעלים (לפי זמן ההמתנה). לחיצה על אריח ה-P1 מציגה את רשימת ה-P1. מסנן לפי טיר. חותמת "עודכן לאחרונה" |
| F3 | **קישור ל-Salesforce** | כל מספר קייס או בקשה הוא קישור לרשומה ב-Salesforce |
| F4 | **כניסה עם SSO של החברה** | Entra ID עם MFA. בלי משתמש וסיסמה נפרדים |
| F5 | **מצב מסך קיר** | תצוגה במסך מלא, בלי תפריטים, עם גופן גדול ורענון אוטומטי |

**ההגדרות** (P1 פתוח, SLA בסיכון, בקשה ממתינה לשיוך, טיר) זהות ל-MVP 2.0, וממומשות ב-views ב-DW. כך אם בעתיד יחזרו ל-Spotfire או יוסיפו אפליקציה לטלפון, המספרים יישארו זהים.

**בחוץ, בכוונה:** בדיוק כמו ב-MVP 2.0: התראת P1, עומס לסוכן, דירוגים, R&D, RingCentral, דוחות PDF ויעדים.

## 4. ארכיטקטורה

```
 Salesforce ──(real-time)──> DW: views on open records (Case, CaseMilestone, Request, names)
                                         │  read-only, Managed Identity
                                         ▼
                              Live API (Azure App Service)
                               - queries the views every 15 s, keeps one snapshot in memory
                               - Entra ID token check, roles: Manager / TeamLead / Kiosk
                               - audit log
                                         │  HTTPS, JSON
                                         ▼
                              Web app (React + TypeScript)
                               - polls the API every 30 s, or gets a push (phase 2: SignalR)
                               - desktop, wall screen, phone browser
                               - every row links to the Salesforce record
```

**למה ככה:**
- **השרת שואל את ה-DW כל 15 שניות, ושומר תמונת מצב אחת בזיכרון.** כל המשתמשים מקבלים את אותה תמונה. כך, גם אם 50 אנשים יפתחו את המסך, ה-DW מקבל שאילתה אחת כל 15 שניות ולא 50.
- **הדפדפן שואל את השרת כל 30 שניות.** זה פשוט ואמין, ומספיק ליעד של עד 60 שניות. אם בעתיד יידרשו שניות בודדות, אפשר להוסיף push מהשרת (Azure SignalR) בלי לשנות את שאר המערכת.
- **הפער בפועל** הוא הפער של ה-DW, ועוד עד 15 שניות בשרת, ועוד עד 30 שניות בדפדפן. כלומר עד כ-45 שניות, בתוספת הפער של ה-DW.

| רכיב | בחירה מומלצת | למה |
|---|---|---|
| ממשק | React ו-TypeScript (Vite) | נפוץ, קל לגייס אליו, והקוד יכול לשמש גם בהמשך |
| שרת | ASP.NET Core (C#) או Node.js על Azure App Service | לבחור לפי מה שצוות IT כבר מכיר. Managed Identity לגישה ל-DW, בלי סיסמאות בקוד |
| הזדהות | Microsoft Entra ID (MSAL), עם תפקידים (app roles) | SSO של החברה, MFA ו-Conditional Access |
| סודות והגדרות | Azure Key Vault | |
| ניטור | Application Insights | זמני תגובה, שגיאות, והתראה ל-IT אם הנתונים ישנים |
| CI/CD | פייפליין אוטומטי, עם סביבת בדיקות וסביבת ייצור | כל שינוי נבדק לפני שהוא עולה |

**ה-API (חוזה ראשוני):**

| Endpoint | מה הוא מחזיר |
|---|---|
| `GET /api/me` | שם, תפקיד וטיר של המשתמש |
| `GET /api/live` | שלושת האריחים, שתי הרשימות וזמן העדכון האחרון (עם סינון אופציונלי לפי טיר) |
| `GET /api/live/p1` | רשימת ה-P1 הפתוחים (עם סינון אופציונלי לפי טיר) |
| `GET /api/health` | מצב השרת וגיל הנתונים (לניטור) |

**זה אותו API שתוכנן לאפליקציית הטלפון (MVP-Mobile).** אם בהמשך בונים גם אותה, השרת כבר קיים.

## 5. אבטחה ודרישות לא פונקציונליות

### 5.1 אבטחה ו-HIPAA
- **צמצום נתונים:** ה-API מחזיר רק את השדות שהמסך מציג: מספר קייס או בקשה, Priority, טיר, מוצר, גרסה, שם בית חולים, שם הבעלים וזמנים. בלי טקסט חופשי ובלי פרטי מטופלים.
- **הרשאות בשרת:** הסינון לפי תפקיד נעשה תמיד בשרת, לא בדפדפן.
- **תקשורת:** HTTPS בלבד, עם כותרות אבטחה (CSP, HSTS). אין שמירה של נתונים בדפדפן מעבר לזיכרון של הדף.
- **ביקורת:** audit log לכל קריאה: מי, מה ומתי.
- **בדיקות:** עמידה ב-OWASP ASVS (רמה 2), ובדיקת חדירות לפני העלייה לאוויר.
- **תשתית:** כל הרכיבים ב-Azure, בתוך ה-BAA של החברה.

### 5.2 דרישות לא פונקציונליות

| דרישה | יעד |
|---|---|
| פער בין שינוי ב-Salesforce לבין המסך | עד 60 שניות ב-95% מהזמן |
| זמן תגובה של ה-API | p95 פחות מ-500 מילישניות (התשובה מגיעה מתמונת המצב בזיכרון) |
| טעינה ראשונה של המסך | פחות מ-3 שניות |
| זמינות | 99.5%, 24/7 (התמיכה עובדת 24/7) |
| דפדפנים | Edge ו-Chrome בגרסה עדכנית, ו-Safari בטלפון |
| תצוגה | מחשב, מסך קיר (1080p ו-4K) וטלפון |
| נגישות | ניגודיות ומקלדת. כל מצב מסומן גם בטקסט ובסמל, לא רק בצבע |

### 5.3 מסך הקיר
מסך קיר הוא בעיה: אין עליו אדם מחובר, ואסור להשאיר עליו משתמש אישי מחובר. **ההמלצה:**
- משתמש ייעודי מסוג Kiosk ב-Entra ID, שיכול לראות רק את המסך החי, ורק לקריאה.
- Conditional Access שמגביל את המשתמש הזה למכשיר אחד מנוהל, ברשת של המשרד.
- ניתוק אוטומטי והתחברות מחדש פעם ביום.
